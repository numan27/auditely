# Public Launch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-out visitor lands on a short page at `/`, audits one website for free without signing up, keeps that audit by signing up, and can read the Terms and Privacy Policy. The owner can see today's free audits and open sign-ups with one switch once the launch checklist is done.

**Architecture:**
- **The free audit.** `POST /api/free-audit` is public. It refuses bots (Vercel BotID) and sites whose name points to a private address, then claims a free audit. The claim is atomic, in Postgres (`claim_free_audit`): one claim per visitor's network per window, and a daily cap across everyone. Then it runs the same `runAudit` the app runs, writes a plain-English summary in Auditely's neutral voice, saves the result in `free_audits`, and sets a signed, httpOnly cookie. A failed audit releases its claim.
- **Keeping it.** The sign-in callback finds the free audit from the cookie, or from a `keep=` value that the magic link carries for a link opened in another browser. It marks the audit taken, atomically, and copies it into the new account's direct-audit search as that user. The visitor's `free_audits` row is never readable by any account.
- **One switch.** `SIGNUPS_OPEN=true` opens sign-ups, shows signed-out visitors the landing page at `/` instead of `/demo`, opens `/signup` and lets search engines in. `FREE_AUDIT_ENABLED` turns the free audit on and off on its own.

**Tech Stack:**
- Next.js 16.3.6 App Router, React 19.2.3, Tailwind 4, vitest 5.
- `@supabase/supabase-js` 2.118, `groq-sdk` 1.2, `stripe` 23.0.1.
- `botid`: the current release, installed in Task 5.
- Playwright, from the npx cache, for the screenshot script and the visual pass.
- Postgres 17 locally (`/usr/local/opt/postgresql@17/bin`), for the migration's scratch check.

**Spec:** `docs/superpowers/specs/2026-10-27-public-launch-design.md`. This plan is Phase 5, "Landing page, free audit and polish". Phases 1–3 are live. Phase 4 (`subscriptions`) waits on the owner's Stripe test key; this branch, `launch`, is cut from it.

**Rulings this plan makes (flag them in review):**
1. **`free_audits` stores the audit result itself, not a `business_id`** (the spec's data model says `ip_hash, business_id, created_at`). A business row needs an owning account (`businesses.user_id` is NOT NULL under RLS), and a visitor has none. The row also holds the website, a status, the summary, and who kept it.
2. **The window counts a visitor's network, not their device:** the IPv4 address, or the IPv6 /64. One phone can't get a new free audit by hopping IPv6 addresses. A household or office shares one.
3. **A claim left `running` for 10 minutes doesn't count.** That is a function that died mid-audit, and the visitor never got a result.
4. **The free audit doesn't count against the new account's 5 audits** when it's kept.
5. **The free audit's summary is written in Auditely's neutral voice** (`AUDITELY_WRITER`), best effort. Without `GROQ_API_KEY`, or when Groq fails, the report shows without "In plain English".
6. **Every audit, not only the free one, now fetches only public addresses.** Redirects are followed by hand, up to 5, and each hop's name is looked up and checked. Signed-in audits had the same gap.
7. **One switch for launch.** `SIGNUPS_OPEN=true` also shows the landing page at `/` and lets robots in. While it's false, signed-out visitors still go to `/demo`, as today.
8. **Billing switches itself off** when production has sign-ups open and a `sk_test_` key (M10). Checkout then says "Billing isn't set up yet", and the error log says why.
9. **Terms and Privacy are a plain-language draft for a lawyer to review.** The operator's legal name, contact email, mailing address and governing state come from the owner (`legal.ts`). Until they're filled in, `docs/launch-setup.md` holds sign-ups closed.
10. **The landing page uses the plans page's feature labels.** "Audit all" becomes "Audit a whole search at once" on both pages.
11. **M8 is folded in** (the live secret key written with `umask 077`), because it's in the same doc step as M7.

## Review Focus

1. **A site whose name resolves to a private address, or that redirects to one.** The free-audit route refuses it before claiming. Inside any audit, a redirect hop to a private host ends that fetch as unreachable. It's never requested. Tests: Task 2 `publicFetch` and Task 5 route.
2. **Two requests at once from one visitor.** `claim_free_audit` serializes claims under one advisory lock, so exactly one runs and the other gets 'visitor'. Test: the scratch check in Task 3, with the second claim made while the first is `running`.
3. **A failed audit doesn't use up the free audit.** `AuditUnavailableError`, any other error, and a failed save all release the claim. No cookie is set, and the message says "This didn't use your free audit." Tests: Task 5.
4. **IPv6 visitors are counted by their /64, and `::ffff:` addresses as their IPv4.** Tests: Task 1 `visitorKey`.
5. **A forged, tampered or foreign cookie or `keep=` value is ignored.** The route runs its normal checks, and the callback keeps nothing. An audit another account has already kept is never copied twice. Tests: Task 1 `readFreeAuditCookie`, Task 5 and Task 6.

**Files:**

**Interfaces:**
- Consumes: `AuditRow` (`audit/types.ts`).
- Produces:
  - **The migration.** One transaction, safe to re-run, with a header in the style of `2026-10-28-usage.sql`.
    - **Guard:** any policy on `free_audits` raises "Other policies would show free audits to an account: …". No account may read the table.
    - **The table:**

      ```sql
      CREATE TABLE IF NOT EXISTS free_audits (
        id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
        ip_hash TEXT NOT NULL,
        website TEXT NOT NULL,
        status TEXT NOT NULL DEFAULT 'running' CHECK (status IN ('running', 'done')),
        audit JSONB,
        report JSONB,
        claimed_by UUID REFERENCES auth.users(id) ON DELETE SET NULL,
        claimed_at TIMESTAMPTZ,
        created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
      );
      CREATE INDEX IF NOT EXISTS free_audits_ip_hash_created ON free_audits (ip_hash, created_at DESC);
      CREATE INDEX IF NOT EXISTS free_audits_created ON free_audits (created_at DESC);
      ```

    - **Access:**
      - RLS on, with no policies;
      - `REVOKE ALL … FROM anon, authenticated`;
      - `GRANT SELECT, INSERT, UPDATE, DELETE … TO service_role`.
    - **The claim function.** `claim_free_audit(p_ip_hash TEXT, p_website TEXT, p_since TIMESTAMPTZ, p_day_start TIMESTAMPTZ, p_daily_cap INT) RETURNS TABLE (id UUID, refused TEXT)`. It is `SECURITY INVOKER`, with `SET search_path = public`. `EXECUTE` is revoked from `PUBLIC`, `anon` and `authenticated`, and granted to `service_role`. In order, it:
      1. takes `pg_advisory_xact_lock(hashtext('free_audits'))`;
      2. deletes rows older than `LEAST(p_since, NOW() - INTERVAL '90 days')`;
      3. deletes `running` rows older than 10 minutes;
      4. returns `(NULL, 'visitor')` when a row for `p_ip_hash` has `created_at >= p_since`;
      5. returns `(NULL, 'cap')` when there are `p_daily_cap` or more rows since `p_day_start`;
      6. otherwise inserts `(ip_hash, website)` and returns `(id, NULL)`.
  - **The store,** in `freeAuditStore.ts` (server-only, `serviceDb`):
    - `type FreeAuditClaim = { ok: true; id: string } | { ok: false; reason: 'visitor' | 'cap' }`.
    - `interface FreeReport { summary: string; improvements: string[]; cold_email: string }`.
    - `interface FreeAuditRecord { id: string; website: string; audit: AuditRow; report: FreeReport | null; createdAt: string; claimedBy: string | null }`.
    - `claimFreeAudit(input: { ipHash: string; website: string; since: Date; dayStart: Date; dailyCap: number }): Promise<FreeAuditClaim>`. It calls the RPC with `p_*` ISO strings, and **throws** on an RPC error.
